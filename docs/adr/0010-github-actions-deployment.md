# ADR-0010: Deployment triggered from GitHub Actions

- **Status:** Accepted, Azure configuration pending (step 12.1 of the guide)
- **Date:** 2026-10-20
- **Deciders:** Ridwane777

## Context

Goal: trigger a deployment **from a link**. Until now, deployment only ran through `scripts/deploy.sh`, from a machine with `az`, `docker` and `kubectl`. Constraints:

- no secret in the repository, history included;
- the repository account has write access to the GitHub repository, **not administration**: it cannot create GitHub secrets;
- the manual procedure in the guide must remain valid.

## Options considered

| Option | ✅ | ❌ |
|---|---|---|
| **A. GitHub Actions, manual trigger (`workflow_dispatch`) + OIDC federated identity** | One link and one button; no stored secret; reuses `scripts/deploy.sh`; every deployment traced (who, when, which commit) | Azure configuration done once by the subscription owner; depends on GitHub Actions |
| B. GitHub Actions with a *service principal* and its password in a GitHub secret | Classic setup | A secret to create (needs admin rights) and rotate; leak risk |
| C. Automatic deployment on every push to `main` | No click | Deploys unintentionally, consumes builds and credit; incompatible with a controlled demo |
| D. Azure DevOps Pipelines | Integrated with Azure | One more tool and account, the code is on GitHub |

## Decision

**Option A**, `.github/workflows/deploy.yml`:

- **manual** trigger only, with two fields: `tag` (empty = current commit) and `rollback` (redeploy without rebuilding, `SKIP_BUILD=1`);
- Azure login through **OIDC**: the identity is only accepted for `repo:Ridwane777/kube-vote-aks:ref:refs/heads/main`, with the *Contributor* role scoped to the `bernstein-spain-rg` group;
- the cluster is started if it is stopped;
- `POSTGRES_PASSWORD` is **generated during the run**. The script only uses it if the Kubernetes Secret does not exist yet, so it is never stored anywhere but Kubernetes;
- `concurrency` prevents two simultaneous deployments;
- the `tag` field is validated before use (characters allowed in an image tag) and passed through an environment variable, never interpolated into the script.

## Consequences

### ✅ Gained

- Deployment and rollback from a browser, with no tool installed.
- No secret created or stored: the IDs in the workflow (client, tenant, subscription) are not secrets.
- A single deployment logic (`scripts/deploy.sh`), for the command line and for the link.

### ❌ Lost / risks

- **Manual Azure configuration** (step 12.1): creating an identity and granting it a role. Not automatable without higher privileges.
- **Anyone who can write to the repository can deploy** and start the cluster, hence consume credit.
- **The password generated by a run could diverge** if it were used to reset an existing database. It is not: it only creates the missing Secret.
- **Slower builds** than locally: GitHub runners have no Docker cache between runs.
- Extra dependency on GitHub Actions, whose enablement for the organisation could not be verified without admin rights.
